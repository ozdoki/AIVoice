# 選択音声編集 Windows QA（#45）

## 基本経路

1. 設定で「選択テキストを音声指示で編集」が既定の `Ctrl + Shift + F9` であり、他の4ショートカットと重複保存できないことを確認する。
2. Notepadで複数行を選択しF9を押す。KoeTypeへ切り替わり、録音中表示が出ることを確認する。
3. 「敬語にして」などの指示を話し、F9を再度押す。原文・音声指示・編集案の必須プレビューが表示され、まだNotepadが変更されていないことを確認する。
4. 置換を実行し、元のウィンドウ・プロセス・選択本文が同一の場合だけ編集案へ置き換わることを確認する。
5. 履歴には「選択音声編集」と音声指示・編集案だけが表示され、原文が保存されないことを確認する。

### 編集品質マトリクス

モデル出力の品質は決定的な単体テストでは保証できない。各対応モデルで、次の固定ケースを実行し、指示以外の意味・固有名詞・数値が変わらず、説明やMarkdown fenceを含まない置換本文だけが返ることを確認する。

| 原文 | 音声指示 | 期待する観点 | 状態 |
| --- | --- | --- | --- |
| この文章は少し長いので要点だけ伝えます。 | 短くして | 要点を保持して短文化 | 未実施 |
| 資料を確認してください。 | 丁寧にして | 意味を変えず敬語化 | 未実施 |
| 準備する。確認する。共有する。 | 箇条書きにして | 3項目を欠落なく列挙 | 未実施 |
| I has two API key. | 英語の文法を直して | 数量を保持して文法修正 | 未実施 |

## 安全な置換とクリップボード

- プレビュー中に選択範囲、本文、対象ウィンドウ、対象プロセスをそれぞれ変更し、置換が拒否されプレビューが残ることを確認する。
- UI Automationで選択範囲を取得できないアプリではCopyのみになり、自動置換が無効であることを確認する。
- 置換成功時に既存のテキスト・画像・ファイル・HTML/RTFクリップボードが変化しないことを確認する。
- Ctrl+Vを部分送信で失敗させ、自動再試行・snapshot復元を行わず、編集案全文がクリップボードに残り、部分入力の可能性が明示されることを確認する。
- Copyを押した場合だけ編集案がクリップボードへ入ることを確認する。

## 排他・キャンセル・期限

- 録音中にEscapeを押し、ASR/API/履歴/置換を行わず元の選択本文が変化しないことを確認する。
- F9停止が先にProcessingへ遷移した後はEscapeで処理を横取りしない。ASRと編集APIは各90秒で打ち切られ、失敗表示後にIdleへ戻ることを確認する。
- 通常録音、処理、修正学習dialog、選択音声編集の録音・previewを相互に開始できないことを確認する。
- F9連打、F9とEscapeの競合、ReplaceとCancelの連打で処理が重複しないことを確認する。
- previewを10分以上放置し、Replaceが期限切れになり、Cancelでは対象へフォーカスを戻せることを確認する。
- トークン改変時に原文・指示・提案を含まない固定エラーとなることを確認する。

## API・保存・Recovery

- APIキー未設定、ASR失敗、編集API失敗、空応答、20,000文字超過で元の選択本文が変化しないことを確認する。
- 選択音声編集では辞書、修正例、スニペット、通常Polish fallback、自動挿入が適用されないことを確認する。
- 設定のデータ処理経路に「選択した原文」と「音声から認識した編集指示」が外部送信対象として明示されることを確認する。
- 失敗Recoveryに原文が含まれず、再文字起こし・再注入が無効、Copyと履歴保存だけが利用できることを確認する。
- 選択音声編集履歴で辞書候補、Polish再実行、修正学習候補が無効であることを確認する。
- ログ、エラー、スクリーンショットへ原文、APIキー、Authorization headerが出ないことを確認する。

実機確認を行った場合は、対象アプリ、取得方式（UIA/Copy fallback）、クリップボード形式、結果、実施日を記録する。未実施項目は互換性を主張しない。

## 実施記録

2026-07-15に最新releaseを起動し、設定画面が読み込めること、修正学習が `Ctrl + Shift + F8`、選択テキスト音声編集が `Ctrl + Shift + F9` と表示されることを確認した。

初回の操作中に押されたEscapeはユーザーから意図しない誤操作だったと訂正されたため、その操作はEscape録音キャンセルの成功事例には含めなかった。

最初のNotepad実施では、UIAで原文を取得しF9の録音開始・停止、正しいpreview表示までは成功したが、Replace後の本文が末尾文字`2`の大量反復へ破損した。Ctrl+Zで原文を復元し、この時点では完了扱いにしなかった。原因調査で、`SendInput`へ渡す`INPUT`のkeyboard unionより大きい未使用領域が初期化されていないことを確認し、`INPUT::default()`で全体をゼロ初期化してからkeyboard fieldをin-place設定するよう修正した。

同日のTauri production release再確認では、当時のUnicode直接入力経路により、Notepadで日本語、英字、数字、絵文字（実際のテスト文字は😃）を含む`日本語 Alice 42 😃`をUIA選択し、F9開始・停止、同文のpreview、Replaceを実施した。全字種が正確に置換された。ただし、その後に置換経路をclipboard paste + 条件付き復元へ変更したため、この結果は新経路の実機確認としては扱わない。

同日、Chromeのローカルdata URL（ページ名 `KoeType Browser QA`）で、textareaの `日本語 Alice 42 😀` とcontenteditableの `日本語 Bob 73 😃` をそれぞれ明示選択した。各ケースでF9により録音を開始し、約1秒後にEscapeでキャンセルした。いずれも原文は変化せず、KoeTypeがIdleへ戻り、エラー表示がないことを確認した。F9の連続押下では2回目が停止操作になるため、初回開始を見落として得た誤判定は実施証拠に含めない。

Chrome専用runtimeは互換性エラーで利用できなかったため、この確認はWindowsのアプリレベルQAとして、既存の業務タブを操作せずに実施した。ChatGPT desktopは安全規約により操作していない。Copy fallback、ChromeでのReplace、上記編集品質マトリクスは未確認のままとする。

このQAでは、選択音声編集の録音中も通常SessionPanelの「待機中」が中央に残り、録音中案内が下部に表示されて見落としやすいことが判明した。そのため、録音中は通常SessionPanelと同時表示せず、main content上部の中央表示を「選択テキストの編集指示を録音中」「F9で編集案生成 / Escapeでキャンセル」へ置き換えるUX修正を行った。停止用F9を受けた後は「編集案を生成中」「音声認識と編集処理を実行中。完了までお待ちください」へ切り替え、追加のF9入力を促さない。preview成功、キャンセル、エラー後は既存SessionPanelへ戻る設計とした。

同日の最新production EXEを使い、ChromeのローカルQAページでcontenteditableのテキストを明示選択した。F9を1回押すと、中央に「選択テキストの編集指示を録音中」「F9で編集案生成 / Escapeでキャンセル」が表示されることを目視確認した。2回目のF9では無音のためASRエラーとなり、即座に待機表示へ戻った。元テキストは変化しなかった。

「編集案を生成中」の処理中画面は表示時間が短すぎたため、今回の実機QAでは目視確認できなかった。recordingからprocessingへの遷移と、完了・エラー後にidleへ戻る表示判定はpure helperの自動テストで確認済みだが、処理中画面の実機目視確認とは区別する。ChatGPTデスクトップ版は操作制約により自動QA対象外とした。
