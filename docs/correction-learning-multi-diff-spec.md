# 修正学習・複数局所差分仕様（#48）

## 1. 文書の目的

本書は、選択テキストから行う修正学習（F8）において、元の音声入力と修正後テキストの間に複数の変更がある場合でも、安全な局所学習候補を抽出・選択・保存できるようにするための仕様を定義する。

対象となる主な不具合は次のとおりである。

- 短い差分や曖昧な差分が1件含まれると、正常に抽出できた他の候補まで全件破棄される。
- 修正後全文と元出力の短い選択範囲を対応付けられてしまい、不正な修正後全文を再構成する。
- 元出力で選択できる範囲が1つだけで、複数の変更を登録する操作が分かりにくい。
- 同じ履歴に対するF8保存が1回に制限され、後から候補を追加しにくい。

本書は実装方法を過度に固定せず、ユーザー操作、データ契約、安全条件、互換性および受入条件を固定する。

## 2. 合意済みの製品判断

以下を本仕様の前提とする。

1. 複数修正は、元全文と修正後全文の比較から複数の局所候補を自動抽出する。
2. 新規自動候補は、信頼度にかかわらず初期状態ではすべて未選択とする。再編集時の保存済みartifactは検証結果に応じて選択候補または既定保持の旧ルールとして扱う。
3. 保存済みの履歴で再度F8を実行した場合、重複レコードを作らず既存レコードの再編集画面を開く。
4. 挿入または削除だけの差分は初回リリースでは自動学習しない。理由を表示し、必要な場合は前後文脈を含む手動置換で補完する。
5. 永続化は既存の `CorrectionRecord` 1件に複数artifactを保持する構造を維持する。候補ごとに別レコードは作らない。

## 3. 用語

- 元全文: 修正元として選んだ音声入力履歴の `final_text`。
- 取得修正テキスト: 外部アプリでユーザーが選択し、F8で取得したテキスト。全文比較では修正後全文、明示範囲比較では修正後抜粋として扱う。
- 修正後全文: 全文比較では取得修正テキストそのもの。明示範囲比較では元全文の選択範囲を取得修正テキストで1回だけ置き換えて再構成した全文。
- 差分ハンク: 元全文と修正後全文の間にある、連続した変更範囲。
- 自動候補: 差分ハンクからシステムが生成した語彙・置換・文体例候補。
- 手動候補: ユーザーが範囲や値を指定して追加・編集した候補。
- 適格候補: 保存可能な安全条件を満たす候補。
- 要確認候補: 対応関係は示せるが、短さ・反復・競合などのため自動的な一般化が安全でない候補。
- 非対応差分: 挿入・削除だけの差分など、現行artifactでは安全に表現できない差分。

## 4. スコープ

### 4.1 対象

- F8で取得した修正後全文と、選択した音声入力履歴の元全文との比較。
- 1つの比較結果からの複数局所置換候補の抽出。
- 短い差分への一意な前後文脈の付与。
- 候補ごとの選択、編集、追加、除外理由の表示。
- 選択した候補だけの保存。
- 同一履歴の既存修正レコードの再編集。
- RawおよびPolishの既存学習artifactとの共存。

### 4.2 対象外

- 正規表現、ファジーマッチ、意味類似による置換。
- 空文字を置換元または置換先にする汎用ルール。
- 複数の非連続テキスト選択をOSから同時取得する機能。
- 自動保存または候補の自動選択。
- schema v2への移行。
- 既存レコードの自動書き換え。

## 5. 基本ユーザーフロー

### 5.1 新規学習

1. ユーザーは外部アプリで、修正を反映した文章全体または変更をすべて含む連続範囲を選択する。
2. F8を実行する。
3. KoeTypeは直近の修正元候補を表示し、ユーザーが音声入力履歴を1件選ぶ。
4. システムは元全文と修正後全文を比較し、複数の局所候補を生成する。
5. UIは候補を変更位置順に表示する。新規自動候補はすべて未選択とする。
6. ユーザーは保存する候補を選択し、必要に応じて手動編集・追加する。
7. UIは選択候補の適用前後と適用範囲を表示する。
8. ユーザーが明示的に保存する。
9. システムは選択候補だけを1件の `CorrectionRecord` に保存する。

### 5.2 部分範囲フォールバック

修正後テキストが元全文の一部だけに対応する場合、ユーザーは従来どおり元出力の対応範囲を1つ指定できる。

- F8ダイアログの既定は「全文から差分を抽出」とする。
- ユーザーはプレビュー前に「全文比較」または「範囲を指定」を明示確定する。
- 自動推定は初期表示の提案にだけ使用でき、preview/createの保存契約には使用しない。
- 「範囲を指定」では、ユーザーが元範囲を確定するまでプレビューしない。
- 全文比較と部分範囲比較のどちらが選ばれているかを画面に明示する。

### 5.3 保存済み履歴の再編集

同じ履歴に対応する有効・無効いずれかの修正レコードが存在する場合、F8は新規作成ではなく再編集として動作する。

- 同一 `source_history_id` の既存レコードが0件なら新規作成、1件ならそのレコードを再編集する。
- schema v1由来で同じ履歴に2件以上ある場合は自動統合せず、状態、更新日時、修正後テキストの抜粋を表示して対象レコードをユーザーに選ばせる。
- 既存の修正後全文とartifactを読み込み、最新の選択テキストとの再比較結果を表示する。
- 保存済みartifactは現previewへ再対応付けする。対応できたものは `persisted_verified` として初期選択し、対応できない旧artifactは `persisted_unverified` として別枠で既定保持する。新規自動候補は未選択とする。
- 追加、変更、削除を保存するまで既存レコードを変更しない。
- 保存時は `id` と `created_at` を維持し、`updated_at` のみ更新する。
- `raw_text`、`original_text`、`mode`、`polish_preset`、`app_process` も既存値を維持する。`corrected_text`、`classification`、`artifacts` だけを最新確認内容へ置き換える。
- `undone` レコードは再編集後も `undone` を維持する。再有効化は別の明示操作とする。
- schema v1では更新前revisionを保持しない。保存前に既存内容を上書きすることを表示する。
- キャンセルまたは検証失敗時は既存レコードを変更しない。
- 同じ `source_history_id` のレコードを複数作成しない。

## 6. 全文・部分範囲の契約

### 6.1 明示モード

preview/createは `comparison_mode` を必須とする。

- `full`: 元範囲を正規化後の元全文全体へ固定する。範囲引数は受け取らない。
- `explicit_range`: ユーザーが確認した非空の元範囲を必須とし、取得修正テキストを修正後抜粋として扱う。
- `explicit_range` の修正後全文は、保存済み元全文の選択開始byteより前のprefix、取得修正テキスト、選択終了byteより後のsuffixを、この順に1回だけ連結して作る。
- `full` では取得修正テキスト、`explicit_range` では上記再構成結果を `CorrectionRecord.corrected_text` へ保存する。
- previewで確定したmodeと、createで指定されたmodeが異なる場合はstale previewとして拒否する。
- 全文と部分範囲の両方が成立し得る場合でも自動確定せず、ユーザーが選んだmodeを画面に表示する。
- 修正後全文を元の短い範囲へ丸ごと挿入する再構成を禁止する。

### 6.2 改行とoffset

- 比較用テキストはCRLFと単独CRをLFへ正規化する。監査用に保存する元・修正後全文は取得時の値を維持する。
- `explicit_range` のtextareaには、バックエンドが返したLF正規化済み `source_display_text` を表示する。
- UIから送る開始・終了は `source_display_text` に対するUTF-16 code unitのend-exclusive offsetとする。
- バックエンドは同じ正規化処理で、表示offsetから保存済み原文のbyte境界への決定的な対応表を生成する。
- CRLF中間、サロゲート中間、書記素クラスタ中間へ対応するoffsetは拒否する。
- preview/createは `source_display_text` のfingerprintも照合し、表示後に原文が変化した場合は拒否する。

### 6.3 不整合の拒否

次の場合は候補を生成しない。

- 元の選択範囲が空、範囲外、UTF-16サロゲートまたは書記素クラスタを分割している。
- 修正後テキストを結合した結果、書記素クラスタ境界が壊れる。
- `explicit_range` で、取得修正テキストが元全文の60%以上、かつ元選択範囲が元全文の60%未満である。この比率はLF正規化後の書記素数で計算する。
- `explicit_range` で、取得修正テキストの先頭または末尾が、選択範囲外の元prefixまたはsuffixと8書記素以上連続一致する。比較可能な範囲が8書記素未満ならこの条件は使用しない。
- 対応位置が複数あり、自動的に一意化できない。

エラーには本文を含めず、「全文比較へ切り替える」「元範囲を選び直す」など次の操作を示す。

## 7. 差分抽出

### 7.1 基本条件

- Unicode書記素クラスタ単位で比較する。
- 同じ入力からは常に同じ候補順・範囲・候補IDを生成する。
- 候補は元全文上の開始位置順、同位置では長い範囲を先に並べる。
- 差分計算には処理量、再帰深度、候補数の上限を設ける。
- 上限到達時は処理を中断し、安全側の警告を返す。全文置換へフォールバックしない。

### 7.2 候補ごとの独立評価

各差分ハンクは独立して評価する。1件が省略・要確認・非対応になっても、他の適格候補を破棄しない。

候補生成と保存可否判定を分離し、少なくとも次の状態を返す。

- `eligible`: 保存可能。
- `needs_review`: 手動確認または文脈拡張が必要。
- `unsupported`: 現行artifactでは安全に保存できない。

各候補は状態に加え、ユーザー向け理由コードと説明を持つ。

### 7.3 短い差分の文脈拡張

置換元が以下の明示条件に該当する場合、候補を即座に破棄せず、変更していない前後文脈を段階的に付与する。

文脈拡張を開始する条件は、LF正規化後の置換元が次のいずれかを満たす場合に限定する。

- trim後の書記素数が2未満。
- 元全文内の完全一致出現数が1ではない。
- trim後のUnicode lowercaseが固定denylist `です`、`ます`、`する`、`これ`、`それ`、`the`、`to`、`of`、`in` のいずれかである。
- Unicode whitespaceだけ、またはASCII punctuationと固定日本語記号 `、。！？・：；（）［］｛｝「」『』【】…—〜～` だけで構成される。

Unicode正規化は行わない。上記以外の「一般語」「助詞」など主観的な分類を実装判断で追加しない。denylistを変更する場合は仕様と境界fixtureを同時に更新する。

文脈拡張は次の順序で決定的に行う。

1. 差分がASCII英数字またはunderscoreの連続token内にある場合、元・修正後の対応token全体まで先に拡張する。token拡張後も上記開始条件のいずれかに該当する場合は停止せず、手順2へ進む。
2. token拡張後も開始条件に該当する場合、またはASCII token内でない場合は、元位置の前1書記素、後1書記素の順に、元・修正後で一致する文脈を1書記素ずつ交互に追加する。
3. 同じ追加数で左右どちらでも一意になる場合は、前方文脈を含む候補を採用する。
4. 拡張が未処理または確定済みの隣接差分へ接触した場合は、両ハンクを統合して先頭から再評価する。
5. LFを含む段落境界、既存上限、または他の非隣接候補を越える必要がある場合は拡張を停止して `needs_review` とする。

文脈拡張は次の条件をすべて満たす最小範囲で停止する。

- trim後の元が2書記素以上であり、固定denylist、whitespaceだけ、記号だけのいずれにも該当しない。
- 置換元が元全文内で一意になる。
- 置換先が修正後全文の対応位置と一致する。
- 隣接候補と範囲が重ならない。
- 置換元・置換先の最大文字数を超えない。
- LFを越えない。

例:

- `件 → 兼` は最小で一意になる `書件 → 書兼` のような文脈を付ける。
- `T → D` は `PTF → PDF` のように単語境界まで拡張する。
- `沖 → 隠岐` は1書記素条件に該当するため、`オービスの沖 → oViceの隠岐` のように接触する周辺変更と統合できる場合は統合する。

境界fixtureとして次を固定する。

- `これは対象です。 → これは対象だ。` のraw hunk `です → だ` はdenylistにより拡張し、最初に一意となる `象です → 象だ`、元範囲 `[4, 7)`、修正後範囲 `[4, 6)`、`eligible/none` を候補とする。
- `値はA。 → 値はB。` のraw hunk `A → B` は1書記素のため拡張し、ASCII token全体でも1書記素のままなので前方へ進み、`はA → はB` を候補とする。
- `項目、次 → 項目。次` のraw hunk `、 → 。` は記号だけのため拡張し、`目、 → 目。` を候補とする。

### 7.4 候補の統合と重なり

- 文脈拡張後の候補範囲が重なる場合は、そのまま複数ルールにしない。
- 接触した隣接差分は先に統合し、安全に再構成できる最小の1候補として再評価する。
- 離れた差分を、変更していない長い文章を含む1候補へ統合しない。
- 統合しても一意性または安全性を満たせない場合は `needs_review` とする。
- 最終的な `from`、`to`、scope、元範囲、修正後範囲が同一の候補は、位置順で最初の1件へdedupeする。

### 7.5 曖昧・反復差分

置換元が全文に複数回現れる場合、位置情報だけを永続ルールへ変換しない。

- 一意になる前後文脈を付与できれば候補化する。
- 文脈を付与できない場合は `needs_review` として未選択表示する。
- 同じ置換元が異なる置換先へ対応する場合は自動保存不可とする。
- ユーザーが手動編集した後も、元全文内での一意性と競合を再検証する。

### 7.6 挿入・削除

- 挿入のみ、削除のみの差分は `unsupported` として位置と理由を表示する。
- 空文字の置換ルールは生成しない。
- ユーザーが学習したい場合は、前後文脈を含む非空の置換元・置換先を手動指定する。
- 手動指定後は通常の一意性、重なり、再構成検証を適用する。

## 8. 候補データ契約

プレビュー専用候補は永続artifactと分離し、少なくとも次の情報を持つ。

- 安定した候補ID。
- artifact案。
- 元全文上の書記素範囲。
- 修正後全文上の書記素範囲。
- 表示用の前後文脈。
- 元全文内の出現数。
- `status: eligible | needs_review | unsupported`。
- 固定enumの `reason_code` と警告。
- 自動生成か手動編集か。
- 既存レコードへ保存済みか。

候補IDを永続artifactのJSON表現や配列indexから生成しない。候補の編集後も、UI上の選択状態を追跡できるdraft IDを別に持つ。

### 8.1 range

- 元範囲と修正後範囲は、LF正規化済み全文に対するUnicode書記素offsetとする。
- 開始を含み、終了を含まないend-exclusive範囲とする。
- UIのUTF-16選択offsetとはバックエンド境界で明示変換する。

### 8.2 reason code

初回実装で少なくとも次を固定snake_case enumとして扱う。

- `none`
- `short_source`
- `ambiguous_source`
- `overlapping_candidate`
- `conflicting_destination`
- `pure_insertion`
- `pure_deletion`
- `meaning_change_suspected`
- `manual_revalidation_required`
- `existing_rule_conflict`
- `candidate_limit_exceeded`
- `diff_budget_exceeded`
- `range_mismatch`

`eligible` は原則 `none`、`needs_review` と `unsupported` は `none` 以外を必須とする。

### 8.3 identityとfingerprint

- `preview_fingerprint` はsource history ID、取得時の元全文byte列、取得修正テキスト、再構成後のLF正規化済み修正後全文、mode、app process、comparison mode、明示範囲を入力とする決定的hashである。
- 再編集previewでは対象record IDと `record_edit_fingerprint` も `preview_fingerprint` の入力に含める。
- 自動candidate IDは `preview_fingerprint`、最終元範囲、最終修正後範囲、candidate kindから生成する。
- candidate IDのhashはidentity用途であり、秘密情報保護の代替には使用しない。
- 手動編集開始時にcandidate IDとは別の不変draft IDを発行する。編集後もdraft IDは維持する。
- 保存済みartifactとの一致は次の型別identityで判定する。
  - vocabulary: trim後のUnicode lowercase。既存の重複判定と一致させる。
  - replacement: `from` exact、`to` exact、scope。前後空白と大小文字を保持する。
  - style example: `input` exact、`output` exact。前後空白と大小文字を保持する。
  - none: typeだけ。
- replacementとstyle exampleをtrimした値で同一視しない。Unicode正規化による暗黙同一化も行わない。

### 8.4 保存済みartifactの状態

再編集時はcandidateの `status` と別に、保存済みartifactへ次の `persistence_state` を付ける。

- `new`: 未保存の自動または手動候補。
- `persisted_verified`: 現previewの元・修正後範囲へ再対応付けでき、新安全検証を通過した既存artifact。
- `persisted_unverified`: schema v1に範囲がなく、現previewへ安全に再対応付けできない既存artifact。

`persisted_unverified` は新規候補ではなく、保持または削除を選ぶ既存ルールとして扱う。artifact identityが1文字でも編集された時点で `new` の手動候補へ変わり、新安全検証を必須とする。

## 9. UI仕様

### 9.1 比較表示

- 元全文と修正後全文を同じスクロール位置で比較できるようにする。
- 各差分を番号付きで示し、候補一覧と本文内の位置を相互に移動できるようにする。
- 色だけに依存せず、`変更前 → 変更後` と状態ラベルを表示する。
- 全文比較中か部分範囲比較中かを見出しで明示する。
- 再構成全文は通常の全文比較では重複表示せず、部分範囲比較時だけ確認用に表示する。

### 9.2 候補一覧

- 新規自動候補は初期状態で未選択とする。
- `eligible` のみ選択可能とする。
- `needs_review` は編集して再検証に成功した後に選択可能とする。
- `unsupported` は選択不可とし、理由と手動補完方法を表示する。
- `persisted_verified` は初期選択し、明示的に解除された場合だけ削除対象とする。
- `persisted_unverified` は候補の選択欄と分けた「既存の未検証ルール」領域に表示し、既定は「変更せず保持」とする。理由、影響scope、現在の修正後全文との対応を確認できないことを警告する。
- `persisted_unverified` の保持・削除controlはcandidateの `eligible` 選択制約とは別である。
- 選択件数と最大16件の上限を常時表示する。
- 新規作成時の保存ボタンは「選択したN件を保存」と表示する。
- 再編集時は「追加N・変更N・削除Nを保存」と表示し、変更が0件なら無効にする。
- 新規作成では0件選択を保存不可とする。再編集では明示的な全削除を許すが、確認後に `none` へ置換するかレコード削除を選ばせ、暗黙には実行しない。

### 9.3 手動補完

- 語彙を追加できる。
- 部分置換を追加できる。
- 自動候補の変更前・変更後・scopeを編集できる。
- 必要に応じて元範囲と修正後範囲の対応を指定できる。
- 編集後は候補を未選択へ戻し、再検証完了後に選択可能とする。
- 自動候補と手動候補が同じ変更を重複して表現する場合は保存不可とする。

### 9.4 アクセシビリティ

- キーボードのみで履歴選択、比較方式切替、候補移動、候補編集、選択、保存、キャンセルを操作できる。
- Tab順は履歴、比較方式、元範囲、候補一覧、候補編集、保存、キャンセルとする。候補一覧内は上下矢印で移動し、Spaceで選択を切り替える。
- 候補の状態と理由は候補ラベルに含め、選択件数とpreview完了は `aria-live="polite"`、保存不能エラーは `role="alert"` で通知する。
- 候補から本文位置へのジャンプはEnterで行い、移動後も候補へ戻る操作を提供する。
- プレビュー再計算でフォーカスを失わない。
- 保存失敗後はダイアログ先頭のフォーカス可能なエラー要約へ移し、候補と選択状態を保持する。
- 高コントラスト表示でも変更箇所と選択状態を識別できる。

## 10. 保存仕様

### 10.1 保存単位

- 1つの `source_history_id` に対し1つの `CorrectionRecord` を維持する。
- 選択した複数候補は1レコード内の複数artifactとして保存する。
- 既存上限どおり、1レコードにつき最大16 artifactとする。
- `none` と他artifactを同時保存しない。
- 新規作成では候補0件の記録だけ保存を行わない。再編集で全artifactを明示削除する場合だけ、確認後に既存レコードを削除するか `none` へ更新するかをユーザーに選ばせる。

### 10.2 部分選択保存の対応検証

選択候補の集合が修正後全文のすべての差分を再現することは要求しない。ユーザーは学習したい候補だけを選べる。

保存時は、選択したreplacement候補を元範囲の開始位置順に並べ、次の手順で `expected_partial_text` を構成する。

1. `source_cursor = 0` とする。
2. 各候補について、元全文の `source_cursor..source_range.start` をそのまま追加する。
3. 修正後全文の `corrected_range.start..corrected_range.end` を追加する。
4. `source_cursor = source_range.end` とする。
5. 最後に元全文の `source_cursor..末尾` を追加する。

`corrected_range` は全差分適用後の修正後全文から置換先文字列を取得するための座標であり、`expected_partial_text` 上の絶対位置ではない。未選択候補の元範囲は元全文の内容と順序を維持する。

同じreplacement集合を、実際の適用処理と同じ「app scope優先、同scopeでは長いfrom優先、一回走査」で元全文へ適用し、次をすべて満たすことを要求する。

- 実適用結果が `expected_partial_text` と完全一致する。
- 選択した各候補の動的な出力位置では、対応する修正後範囲から取得した文字列と完全一致する。
- 選択範囲のunion外からコピーしたsource sliceは、内容と相対順序が元全文と完全一致する。
- 各候補を1件ずつ除いて再適用した結果が同一なら、その候補を非寄与として拒否する。

加えて、各選択artifactについて次を検証する。

- プレビューで提示された候補、または同じプレビュー内で検証済みの手動候補である。
- 元範囲と修正後範囲が対応し、候補の `from` と `to` がその範囲に一致する。
- 置換元が元全文内で一意、または一意な文脈を含む。
- 元の選択範囲外へ意図せず適用されない。
- 他の選択artifactと重複、shadow、循環、競合しない。
- 実際の置換優先順位で適用しても、各候補が自身の対応範囲へ寄与する。

監査用の `original_text` と `corrected_text` は全文のまま保存し、選択したartifactが全文差分の一部だけであることを許容する。

語彙と文体例は `expected_partial_text` のreplacement再構成には参加させず、型別の対応検証を行う。

再編集の `persisted_unverified` だけは、artifact identityと順序を一切変更せず保持する場合に限り、新しい範囲対応検証をgrandfatherしてよい。値、型、scope、順序の変更、複製、別recordへの移動はgrandfather対象外であり、手動候補として新安全検証を必須とする。

`persisted_unverified` を保持したまま `corrected_text` を更新する場合、最新の監査全文と旧artifactの対応を確認できないことを保存確認へ明示する。schema v1ではartifactごとの旧revisionを保持できないため、無警告の上書きを禁止する。

### 10.3 語彙と文体例

- 本仕様では語彙を自動抽出せず、手動候補だけとする。
- 語彙は選択candidateの修正後範囲内に、trim後の値が大文字小文字を含め完全一致する連続文字列として存在する場合だけ保存可能とする。
- replacementを1件も選ばず語彙だけを保存する場合は、語彙を含む差分candidateをUI上で対応元として指定する。
- 語彙のidentityと上限判定では既存互換のtrim・Unicode lowercaseを用いるが、本文との対応確認はcase-sensitiveとする。Unicode正規化による暗黙変換は行わない。
- Rawでは文体例を保存しない。
- Polishの全文比較では従来の全文style候補、明示範囲比較では元抜粋・修正後抜粋の局所style候補だけを許可する。
- Polish styleは対象pair自体を分類し、`meaning_change_suspected` の場合は生成・保存しない。
- styleはpreviewで生成された入力・出力、preset、app process、範囲と一致する場合だけ保存可能とする。
- 文体例や語彙だけを選択する場合も、元・修正後との型別対応関係を検証し、無関係な値を保存できないようにする。
- 語彙・文体例が外部APIへ送信される可能性を保存前に表示する。

### 10.4 競合と冪等性

- 保存時に履歴内容、修正後全文、comparison mode、明示範囲、preview fingerprintがプレビュー時と一致することを確認する。
- `record_edit_fingerprint` は対象recordのID、status、corrected text、classification、artifactの型・値・順序、updated atをcanonical serializationして作る。時刻だけをversionとして使用しない。
- 再編集previewは対象recordの `record_edit_fingerprint` を保持する。update直前にcorrections storeの排他lock内で現在値を再計算し、不一致ならlost updateとして保存せず再読み込みを求める。
- 新規作成previewは同一source history IDを持つrecord一覧のcanonical fingerprintを保持する。create直前に同じstore lock内で再確認し、recordの追加・削除・更新があれば新規作成せず再previewを求める。
- preview開始時に以前の確認状態を破棄し、成功後のみ保存可能状態にする。
- preview fingerprintの有効期間は既存pendingと同じ10分とし、期限切れ後のcreateを拒否する。
- UIはpreview要求ごとに単調増加request IDを付与し、最新request ID以外の応答を表示・保存可能状態へ反映しない。
- preview成功時に推測困難な `idempotency_key` を発行し、createで必須とする。
- create直前に、preview fingerprint、対象record IDとversion、create/update/delete/noneの操作種別、選択artifactの型・値・scope・順序をcanonical serializationした `create_request_digest` を計算する。
- 保存成功時はpending本文と候補本文を直ちに破棄し、`idempotency_key`、preview fingerprint、create request digest、record ID、本文を含まない成功結果だけをプロセス内replay cacheへ10分保持する。
- 同じ `idempotency_key`、fingerprint、create request digestのcreate再送は書き込みを行わず、最初と同じrecord IDと成功状態を返す。
- 同じkeyでfingerprintまたはcreate request digestが異なる場合、または別keyで消費済みtokenを使用した場合は拒否する。
- replay cacheはプロセス再起動をまたがない。再起動後の再送は通常の既存レコード再編集契約で扱い、自動追記しない。
- 二重クリックや再送で重複レコード・重複artifactを作らない。
- 保存はストア単位で全成功または全失敗とする。
- 書き込み失敗時に既存レコードを失わず、UIの選択状態を保持する。

## 11. 適用範囲と将来の置換

- 自動候補の既定scopeは入力先アプリが判明している場合 `app`、不明な場合 `global` とする。
- `global` への変更はユーザーが明示的に行う。
- 置換は完全一致を基本とし、正規表現・曖昧一致へ自動変換しない。
- app固有ルールをglobalより優先し、同scope内では長い置換元を優先する既存規則を維持する。
- 同じ `from` に異なる `to` がある競合を保存しない。
- 7.3の明示条件に該当する短い文字列、固定denylist、記号だけの置換は文脈なしで保存しない。

## 12. 上限・性能

- 元全文・修正後全文は既存どおりUnicode scalar valueで最大20,000文字とする。UIのUTF-16 `maxLength`だけを権威にせず、バックエンド検証を正とする。
- 差分計算は最大2,000,000 operations、最大再帰深度256とする。
- 長文・反復入力・敵対的入力でもUIを長時間ブロックしない。
- 差分ハンクは位置順で最大64件まで評価し、それ以降は `candidate_limit_exceeded` として集計する。
- プレビューで表示する候補数と検出総数・省略数を分け、常に `total = displayed + omitted` を満たす。
- 保存可能artifactは最大16件とし、超過候補は理由付きで未選択または省略表示する。
- 上限到達時に候補を黙って切り捨てない。
- 既存上限の500 records、5MiB store、vocabulary 128文字、replacement from 128文字、replacement to 2,000文字、style 8,000文字、active replacement 500件、style有効3件・合計6,000文字を維持する。
- Windows実機QAでは、20,000文字の末尾付近1変更を2秒以内、反復を含む敵対入力を5秒以内に警告またはpreviewへ収束させることを目標とし、測定機種と結果をQA記録へ残す。正しさの判定はwall-clockではなくoperation上限を用いる。

## 13. エラー・警告

最低限、次の理由を区別して表示する。

- 元と修正後が同一。
- 全文と部分範囲の対応不整合。
- 意味変更の疑い。
- 短すぎる差分。
- 反復していて一意でない。
- 挿入・削除のみで非対応。
- 候補範囲の重複または競合。
- 候補数・文字数・計算量上限。
- stale previewまたは履歴内容変更。
- 同一履歴の既存レコードを再編集する必要がある。
- 永続化失敗。

警告は候補全体と候補個別を分け、本文・APIキー・選択テキストをログや固定エラーへ含めない。

## 14. データ・互換性

- `CorrectionStore` schema v1を維持する。
- `CorrectionRecord` の既存必須フィールドを変更しない。
- 複数候補は既存のartifact配列で表現する。
- 候補範囲、状態、理由、draft IDはプレビュー専用とし、永続化を必須にしない。
- 既存の長文置換、語彙、文体例、無効レコードを読み込み・編集・保存できることを維持する。
- 新しい候補安全検証は新規createと、本仕様によるupdateで追加・変更されたartifactに適用する。identityと順序を変えず保持する `persisted_unverified` は前節のgrandfather契約を適用する。schema v1 loadでは従来の構造、文字数、store整合性検証だけを行う。
- 既存の `none`、全文に近いreplacement、同一sourceの複数recordをload時に拒否・変換・統合しない。
- 更新対象以外のrecordはJSON上の意味値と配列順を維持する。
- 旧storeを読み込み、新しい複数artifactレコードを追加または更新し、保存・再読込後も旧レコードが変化しないことを確認する。
- 新機能を無効化しても、保存済みartifactは従来の適用処理で使用できる。

## 15. セキュリティとプライバシー

- 元全文、修正後全文、候補値をconsoleやRust logへ出力しない。
- エラーには本文を含めない。
- F8 pending本文は期限切れ、キャンセル、保存成功時に破棄する。
- APIキーや設定済みsecretが元・修正後・artifactへ混入している場合は保存を拒否する。
- 語彙・文体例の外部送信可能性を保存前に明示する。
- 修正前後全文はローカルへ平文保存されることを明示する。

## 16. 受入条件

### 16.1 代表例

次のfixtureを固定する。rangeはLF正規化済み全文上の書記素offset、end-exclusiveである。

```text
original_full:
  オービスの沖です。お見積書件注文書です。PTFを来週中をめどに返送。
corrected_full:
  oViceの隠岐です。お見積書兼注文書です。PDFを来週中を目途に返送。
comparison_mode: full
expected_candidates:
  - artifact: replacement(app, "オービスの沖", "oViceの隠岐")
    source_range: [0, 6)
    corrected_range: [0, 8)
    status: eligible
    reason_code: none
  - artifact: replacement(app, "書件", "書兼")
    source_range: [12, 14)
    corrected_range: [14, 16)
    status: eligible
    reason_code: none
  - artifact: replacement(app, "PTF", "PDF")
    source_range: [20, 23)
    corrected_range: [22, 25)
    status: eligible
    reason_code: none
  - artifact: replacement(app, "めど", "目途")
    source_range: [28, 30)
    corrected_range: [30, 32)
    status: eligible
    reason_code: none
expected_total: 4
expected_omitted: 0
initial_selection: []
```

候補IDの文字列表現自体は固定しないが、同じfixtureを複数回previewした際に完全一致すること。

候補1と3だけを選んだ場合の `expected_partial_text` は次とする。

```text
oViceの隠岐です。お見積書件注文書です。PDFを来週中をめどに返送。
```

候補3だけを選んだ場合、候補3の修正後全文上のrangeは `[22, 25)` のままだが、動的な部分適用結果は次とする。

```text
オービスの沖です。お見積書件注文書です。PDFを来週中をめどに返送。
```

1文字差分を安全な文脈へ拡張できない別fixtureでも、他の候補が消えないこと。すべての新規候補は初期状態で未選択であること。

### 16.2 単体・プロパティテスト

- 単一差分、複数差分、隣接差分、離れた差分を決定的に抽出する。
- 有効な3差分と短い1差分が混在しても、有効3件を保持する。
- 短い差分を最小の一意文脈へ拡張する。
- 反復語句が一意化できなければ未選択の要確認候補にする。
- 同じ置換元が異なる置換先へ対応する場合は保存不可にする。
- 挿入のみ、削除のみを自動保存しない。
- 句読点、空白、改行、日英混在、結合文字、濁点結合形、ZWJ絵文字、肌色修飾、国旗で書記素境界を壊さない。
- 20,000文字、反復文字列、候補上限超過でも処理量上限内で終了する。
- 候補の一部だけを選択して保存できる。
- 未選択候補があっても、選択候補の対応関係が正しければ保存できる。
- 手動編集した候補が無関係、非寄与、shadow、範囲外なら拒否する。
- CRLF、LF、非BMP文字を含むtextarea選択をUTF-16 offsetから元byte範囲へ往復できる。
- 全文と部分範囲の両方が成立し得る場合も、明示したcomparison mode以外では保存されない。
- 4候補中1件だけ、および任意の2件だけを保存した期待部分適用結果が一致する。

### 16.3 コマンド・永続化テスト

- previewとcreateの履歴ID、UTF-16範囲、全文fingerprintの不一致を拒否する。
- 保存済み履歴でF8を実行すると既存レコード更新となり、重複しない。
- active、undone、同一sourceに複数あるlegacy recordをそれぞれ仕様どおり再編集できる。
- legacyの短い・反復・全文に近いreplacement、および最新captureへ対応しないvocabulary/styleを `persisted_unverified` として無変更保持でき、暗黙削除しない。
- `persisted_unverified` を編集するとgrandfather対象から外れ、新安全検証を通らなければ保存できない。
- `persisted_verified` は初期選択され、明示解除した場合だけ削除される。
- 更新失敗時に既存レコードが維持される。
- 更新失敗前後で対象recordとstore内の非対象recordがdeep equalである。
- 再編集preview後に対象recordを設定画面など別経路から更新した場合、record edit fingerprint不一致でF8 updateを拒否し、先行更新とF8側の未保存内容のどちらも失わない。
- 新規create preview後に同一sourceのrecordが別経路で追加・更新・削除された場合、source record一覧fingerprint不一致でcreateを拒否し、重複recordを作らない。
- 二重保存で重複artifactを作らない。
- 同一idempotency key・fingerprint・create request digestの二重送信は冪等で、いずれかが異なる再送は拒否する。
- schema v1の旧storeをロード、更新、保存、再ロードして旧データが完全一致する。
- Rawでstyleを、Polishで未生成styleを保存できない。

### 16.4 UI・Windows実機QA

- 全文比較で複数候補が位置順に表示される。
- 新規自動候補はすべて未選択で、新規作成時は0件では保存できない。
- 再編集では `persisted_verified` が初期選択され、明示的に解除しない限り削除されない。
- `persisted_unverified` は選択候補と分離され、既定保持となり、明示的に削除しない限り変更されない。
- 候補選択、編集、再検証、保存をキーボードだけで完了できる。
- 元の短い範囲と修正後全文の不整合が明示エラーになる。
- 保存失敗後も候補と選択状態が残る。
- 保存済み履歴をF8から再編集できる。
- Escape、キャンセル、背景クリック、10分期限切れでpendingが破棄される。
- プレビュー中の履歴切替や再選択でstale結果が表示されない。
- 高DPI、ウィンドウ最小サイズ、長文スクロールで候補操作が隠れない。
- スクリーンリーダーと高コントラストで状態を識別できる。
- NVDAの最新版、Windows表示倍率100%と200%、サポート対象の最小ウィンドウ寸法でフォーカス順と操作可能性を確認する。

## 17. ロールアウトとロールバック

- 新しい複数差分抽出とUIは機能フラグ下で導入する。Windows実機QAと独立レビュー完了までは既定無効、完了後に既定有効へ切り替える。
- 単一差分、複数差分、短い差分、反復差分の順に検証範囲を広げる。
- ロールバック時は従来の単一範囲previewへ戻せるようにする。
- 永続schemaを変更しないため、新機能で保存済みのartifactはロールバック後も通常ルールとして利用できる。
- ローカルの実ユーザーデータを使うQAは行わず、専用のapp-dataディレクトリまたはテスト識別子を使用する。

## 18. 完了条件

次をすべて満たした時点で本仕様の実装を完了とする。

1. 代表例から複数候補が抽出され、短い差分が他候補を消さない。
2. 新規自動候補が未選択で表示され、選択した一部だけを安全に保存できる。再編集では既存artifactのverified/unverified状態を仕様どおり維持できる。
3. 修正後全文と短い元範囲の誤対応を拒否できる。
4. 同一履歴をF8から再編集でき、重複レコードを作らない。
5. schema v1と既存修正レコードの互換性が維持される。
6. 自動テスト、Windows実機QA、独立レビューでブロッカーがない。
7. 機能フラグの有効・無効の両方で起動・既存データ読込・ロールバック経路を確認できる。
